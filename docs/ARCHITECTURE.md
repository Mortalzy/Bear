# Архитектура Bear

## Границы первого этапа

Один репозиторий, npm workspaces, JavaScript ES modules.
React + Vite для клиента, Express для API.
Общие правила вынесены в @bear/shared, чтобы клиент и сервер использовали одинаковые значения.
Дизайн текущей страницы технический и подлежит замене после согласования.

## Текущий API

| Метод | Путь | Поведение |
| --- | --- | --- |
| GET | /api/health | Процесс доступен; requestsEnabled=false |
| GET | /api/config | Несекретные настройки и правила файлов |
| POST | /api/requests | 503 REQUESTS_UNAVAILABLE; ничего не сохраняется |

Health — проверка процесса, не подтверждение готовности почты.
Клиент не вызывает POST и не отправляет файлы.
Маска телефона, согласие, удаление отдельных выбранных файлов и реальная отправка ещё не реализованы.

## Следующий этап

Форма отправляет multipart/form-data: name, phone, email, description, consent, files.
Принимать несколько файлов, не более 50 000 000 байт каждый.
Начальный предел 5 файлов / 250 000 000 байт — настраиваемый параметр проекта.
Проверять реальные байты на сервере; клиентская проверка metadata только для удобства.
Форматы: DWG, DXF, STEP, PDF, JPG. Дополнительные форматы — отдельное решение.

До включения endpoint:
- Проверка полей, согласованного текста согласия и ограничение частоты до чтения файлов.
- Потоковая запись на постоянный диск вне публичной директории; лимит всего запроса с учётом multipart.
- Ограничение дисковой квоты и параллельных загрузок; очистка оборванных загрузок.
- Проверка формата, безопасные имена, запрет исполнения/публичного просмотра.
- Письмо через Nodemailer, получатель только из серверной конфигурации, Reply-To из проверенного email.
- Скачивание по случайному токену, проверка срока, Content-Disposition: attachment.
- Срок хранения и резервирования согласовать; 30 дней пока только предложение.
- Хранить минимум служебных данных на диске, без отдельной СУБД.
- Защита от повторного запроса; явно обрабатывать неопределённый результат SMTP после таймаута.
- Успех только после сохранения и приёма письма SMTP; это не гарантия папки «Входящие».
- Проверить доставку реальным тестом с разрешения владельца.

## Размещение

Планируется один VPS: Nginx выдаёт client/dist и передаёт /api на Express.
Node-процесс управляется systemd. HTTPS, постоянное хранилище, очистка и резервирование добавляются позже.
Не размещать .env и файлы заявок в публичной директории или Git.
robots=noindex в черновике; перед публикацией заменить после проверки контента.

## Зависимости и проверки

Версии ограничены совместимыми major-диапазонами. Lockfile нужно получить и проверить в доступной Node-среде.
До фиксации lockfile CI использует npm install; затем перейти на npm ci.
CI выполняет тесты правил и HTTP-контракта, затем production-сборку клиента.
SMTP, загрузка реальных файлов и визуальная проверка не покрыты этим этапом.
