# Минимальная защита BEAR

## Что включается вместе с API

- Helmet добавляет защитные HTTP-заголовки; HSTS для публичного сайта задаёт HTTPS-конфигурация Nginx.
- Все пути `/api` вместе ограничены 120 запросами в минуту на один процесс. Это также ограничивает рост хранилища лимитов формы.
- Форма допускает 5 попыток в час с одного IPv4-адреса или IPv6-сети /64. Ошибочные попытки тоже учитываются. При превышении сервер возвращает 429 и `Retry-After`.
- Лимитер автоматически освобождает просроченные записи, не сбрасывая все ограничения при появлении новых IP. Перезапуск процесса сбрасывает счётчики. Для нескольких процессов потребуется общее хранилище.
- Одновременно обрабатываются максимум две заявки, включая отправку SMTP. Занятый сервер отвечает 503 с `Retry-After: 10`.
- Загрузка ограничена 120 секундами и 19 000 000 байтами тела multipart, включая служебные данные. Размер считается и для запросов без `Content-Length`. При превышении соединение прерывается; Multer закрывает потоки, а временная папка удаляется. Лимит самих вложений остаётся 18 МБ суммарно, до 5 файлов и не более 25 МБ на отдельный файл; фактически суммарный предел ограничивает и один файл.
- Недопустимое расширение отклоняется до записи файла. Поддерживаемые форматы дополнительно проверяются по сигнатуре; файлы не публикуются и передаются только вложениями в письме.
- SMTP ограничивает установку соединения и ожидание приветствия 10 секундами, простой сокета — 30 секундами. Это не гарантия доставки письма во «Входящие».
- HTTP-сервер задаёт ограничения времени приёма заголовков/тела, простоя и повторных запросов через одно соединение.

## Nginx при размещении на VPS

Шаблон `deploy/nginx/bear.conf` ещё не установлен на публичном сервере. Он рассчитан на один домен, Nginx и один процесс Node.js на одной машине, без внешнего CDN/прокси.

1. Заменить `bear.example.ru`, пути к сертификату и `/var/www/bear` на реальные значения. Сначала выпустить сертификат: до его появления использовать HTTP-конфигурацию для ACME с каталогом `/var/www/letsencrypt`. Затем включить полный HTTPS-шаблон.
2. Выполнить `npm ci` и `npm run build`. Nginx должен читать `client/dist`, а временные файлы должны лежать вне него.
3. В `server/.env` оставить `HOST=127.0.0.1`, `PORT=3001` и указать `TRUST_PROXY=loopback`. Без `TRUST_PROXY` приложение не доверяет прокси-заголовкам. Не открывать порт 3001 в интернет.
4. Подключить шаблон в контексте `http` Nginx, проверить `sudo nginx -t`, затем выполнить `sudo systemctl reload nginx`. Убедиться, что другой конфиг не перехватывает этот домен.
5. Проверить HTTPS, страницу, карусели с видео, заявку с файлами и ответ 429 после шестой попытки с одного IP. Nginx перезаписывает `X-Forwarded-For`, поэтому присланный посетителем заголовок не меняет его адрес в лимитере.

Nginx ограничивает API по IP и суммарно, буферизует загрузки, выставляет предел тела запроса, таймауты и защитные заголовки для самого frontend. Статические фотографии и видео имеют кеширование; для них не применяется строгий лимит частоты API. Если перед сервером появится внешний прокси, схему определения IP нужно пересмотреть до подключения.

## Возможности и эксплуатация

Эта конфигурация уменьшает последствия спама и небольшой перегрузки запросами. Мощные сетевые DDoS-атаки должен отражать провайдер до попадания трафика на VPS. При устойчивой распределённой HTTP-атаке понадобится внешняя защита L7.

Перед размещением закрыть лишние порты, использовать SSH-ключи, запускать Node.js от отдельного пользователя и обновлять ОС. Включить ротацию журналов Nginx и приложения, следить за свободным диском и доступностью. Секреты SMTP хранить только в исключённом из Git `server/.env`.

Капча и отдельная антибот-система на этом этапе не добавлены. Проверка сигнатуры файла не заменяет антивирусную проверку вложений.
